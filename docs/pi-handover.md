## Situation

**GitHub Actions minutes ran out on 2026-07-28 ~10:00 UTC.** Every `dbt run` and
`Claim PDF worker` run since then has failed at dispatch (`runner_id: 0`, no
runner assigned, dead in seconds, no logs). This is account-level, not a code
bug. It is the second time minutes have forced a product decision — see
CLAUDE.md §3, which records cutting `dbt build` from 15 min to hourly on
2026-07-07 for the same reason.

**Measured cause:** `dbt-run` alone is ~81 % of the burn (24 runs/day × 3 billed
minutes ≈ 2 160/month, of ~2 685 total against a 2 000 quota). Everything else is
noise by comparison.

**The fix being built:** move `dbt-run` — and only `dbt-run` — onto a Raspberry Pi
4 the user already owns, registered as a self-hosted GitHub Actions runner, with
GitHub-hosted runners kept as an automatic failsafe. Full reasoning, measured
numbers and the failsafe design are in `docs/pi-runner-plan.md`. Read it before
starting; do not re-derive the scope decision.

**Current data state (checked 2026-07-29 ~12:20 CEST):** the previous session
manually refreshed `int_stop_events` and `fct_claimable_stop_events` through the
Supabase SQL API to unfreeze the board. `v_journeys` and `v_claimable_journeys`
are current; grain, duplicate-key and
`assert_claimable_layer_covers_fct_journeys` checks all passed afterwards.
`int_stop_events` was 70 min old at handover against a 360 min watchdog
threshold — **so the board goes stale again roughly 5 hours after that unless
something runs `dbt build`.** Getting the Pi to the point where it can run
`dbt build` by hand is therefore both Phase 1 and the immediate bridge.

Ingestion is unaffected throughout — the pg_cron collectors live inside Supabase.

## The task

Ordered. Stop and ask rather than guess if something does not match.

1. **Flash the SD card.** Ubuntu Server 24.04 LTS arm64. Either drive
   `rpi-imager --cli` yourself (needs elevation) or have the user do it through
   the Imager GUI — the GUI's gear panel is the lower-risk path because it writes
   the cloud-init user/SSH/hostname config correctly without hand-authored YAML.
   Settings: hostname `qvitta-pi`, the user's account, **SSH enabled** (key
   preferred). Ethernet, so no Wi-Fi config.

   If you hand-write cloud-init `user-data` instead, be aware it **overwrites**
   Imager's — you must reproduce the user and SSH key or the Pi becomes
   unreachable and needs re-flashing.

2. **User plugs it in.** Card into the Pi, ethernet, power. Wait ~2 min for the
   first-boot filesystem expansion and reboot.

3. **Confirm SSH:** `ssh <user>@qvitta-pi.local`. If mDNS does not resolve, find
   the lease on the router. Then ask the user to set a **DHCP reservation** so
   the address is stable.

4. **Run the bootstrap.** The repo is **private**, so the raw GitHub URL will not
   work unauthenticated — clone the repo on the Pi first, or paste the script
   over SSH. `bash pi-bootstrap.sh`. It handles apt upgrade, ufw, journald/zram/
   noatime, DNS pinning, the dbt venv and the repo clone.

5. **Write `~/.dbt/profiles.yml`** from the template in `docs/pi-setup.md` §5.
   Needs the **session pooler** credentials — port **5432**, *not* the
   transaction pooler on 6543, which breaks dbt's multi-statement transactions.
   Same values as the `SUPABASE_DB_*` repo secrets. `chmod 600` it.

6. **Run `dbt build`** from `/opt/qvitta/repo/dbt` using
   `/opt/qvitta/dbtvenv/bin/dbt`. **This is the Phase 1 exit criterion**, and it
   also re-freshens the stale board. Report what it does.

7. **Register the runner** — GitHub → Settings → Actions → Runners → New
   self-hosted runner → **ARM64**. Registration token is valid one hour, so
   generate it when actually ready. Register with `--name qvitta-pi --labels
   qvitta-pi` (the label is load-bearing: Phase 2's router dispatches
   `runs-on: qvitta-pi`). Install as a service via `svc.sh` so it survives
   reboot. Leave it **idle** — no workflow targets it until Phase 2.

8. **Optional, if the user wants them:** AdGuard Home (`docs/pi-setup.md` §7) and
   Claude Code CLI + Remote Control (§9). Both are genuinely optional; neither
   blocks Phase 2.

## Hard constraints

- **NEVER run `dbt build --full-refresh`.** Several models accumulate history
  beyond what raw retention can rebuild — `fct_claimable_stop_events` holds a
  91-day claim window against ~5 days of `int_stop_events`, plus the SEO aggs. A
  full refresh silently and permanently destroys the difference. CLAUDE.md §10
  and §15.
- **Do not push to `main`.** Branch `claude/raspberry-pi-github-actions-nyu361`.
- **Do not move `claim-pdf-worker` or `claim-canary` to the Pi.** Deliberate
  scope decision, reasoning in `pi-runner-plan.md` §2. Deferred, not forgotten.
- **Do not re-add a `schedule:` block to `dbt-run.yml`.** It is fired externally
  by cron-jobs.org; re-adding it double-fires. CLAUDE.md §3.
- Read CLAUDE.md before touching anything under `dbt/` or `supabase/migrations/`.

## Corrections already discovered — do not rediscover these

1. **`apt install python3.11` fails.** Ubuntu 24.04 ships 3.12 and does not
   package 3.11. Use the system `python3`. dbt runs fine on 3.12.
2. **Therefore Phase 2 should bump `dbt-run.yml` from `python-version: '3.11'`
   to `'3.12'`** rather than pulling deadsnakes and hand-seeding the runner tool
   cache. `ubuntu-latest` has 3.12 too, so both runners match and the tool-cache
   unknown disappears. This was the only genuine unknown flagged in Phase 1.
3. **`systemd-resolved` holds port 53**, so AdGuard cannot bind until
   `DNSStubListener=no`. The bootstrap already does this.
4. **The Pi must not resolve DNS through its own AdGuard.** If it does, a
   blocklist false positive or an AdGuard restart breaks the Pi's ability to
   resolve the Supabase pooler and `api.anthropic.com`, and dbt fails with a DNS
   error whose cause is an unrelated service on the same box. The bootstrap pins
   `DNS=1.1.1.1 9.9.9.9` for the Pi itself; other LAN devices still filter.
5. **AdGuard makes the Pi network-critical.** Phase 2 includes deliberately
   powering the Pi off to prove the failsafe works — that will also kill DNS for
   the house. Warn the user before doing it.
6. **Claude Dispatch does not work on a headless Pi** — it drives the Claude
   Desktop GUI app. **Remote Control** is the CLI equivalent and is the right
   tool. `docs/pi-setup.md` §9.
